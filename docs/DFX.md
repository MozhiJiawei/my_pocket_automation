# DFX 结果与故障处理

每轮归档源码包、哈希清单、无授权信息的运行配置、设备日志截图和 `result.json`。账号身份特征及授权继续保留在仓库外。

## 如何判断结果

| 字段 | 含义 |
| --- | --- |
| `host_status` | 电脑端完成、启动未知、超时、通信失败或业务证据不足 |
| `launch_status` | 未尝试、已接受、响应未知；响应未知不代表没有启动 |
| `script_status` | 设备日志证实正常退出、失败，或证据不足 |
| `business_status` | 已观察、运行中、完成、未全部实现、暂停、阻塞或失败 |
| `termination_reason` | 设备业务终止原因；同时保留原始 `device_summary` |
| `last_device_status` / `may_still_be_running` | 最后观察到的设备状态，以及是否可能仍在运行 |
| `collection_status` | 采集是否尝试、完成或失败；完成不保证业务证据充分 |
| `expectation_met` | 已取得的证据是否符合本次调测步骤，不等同整日成功 |

主循环完成当前副本范围时，其他任务仍为 `not_implemented`，因此业务状态是 `incomplete`，`daily_complete` 保持 false。主循环或完整副本步骤遇到暂停，电脑端返回失败；单步调测只有符合该步骤明确预期原因的暂停才接受，未知画面暂停不能冒充预期结果。

调用启动入口前先记录“启动未知”。响应丢失、等待超时或通信失败后，尽力查询设备状态并采集本轮证据，持久化异常结果；不自动重发启动、不覆盖可能仍运行的代码。异常信息只记录类型，避免归档授权信息。采集或清理的次生异常不能覆盖首个异常。

`ts-cli.ps1 deploy/run` 共用已认证的空闲检查，只有状态 `f00` 才发布。直接 `deploy` 因此也需要 `TOUCHSPRITE_AUTH`；通过 `run-daily.py` 使用现有外部授权即可。设备状态未知时拒绝发布。采集不需要授权。

Lua 故障处理分别尝试写首个错误、保存截图、记录退出；某一路失败不会阻止其他诊断。文件日志不可用时尝试 `nLog`，但不保证电脑端能取得该输出。配置加载等早期错误可能没有设备日志，运行器必须判为证据不足，并保存电脑端结果。

## 离线验证

2026-10-09：45 个测试全部通过，其中新增 24 个 DFX 用例，原有 21 个副本识别、保护和语法回归也通过。

```powershell
python scripts/device/build.py
python -m unittest discover -s tests -p "test_*.py"
```

- `test_dfx_runner.py`：模拟发布／设备／采集，注入响应丢失、等待超时、通信错误、采集超时、清理失败、缺失日志和业务暂停，验证每轮持久化结果、保留首个错误且不重发启动。
- `test_dfx_device_failures.py`：执行真实 Lua 入口，替换设备及任务能力，验证日志／截图失败和初始化错误的诊断兜底、返回主页失败的显式结果。
- `test_dfx_publish.py`：执行实际 PowerShell 发布决策块，替换 API 和发布动作，验证忙碌／未知状态拒绝发布、空闲部署不启动、空闲运行仅启动一次；AST 检查不存在另一处绕过检查的发布调用。

这些测试不调用 ADB、HTTP，不读取真实授权或角色资料，不启动副本。本轮只在本地构建，没有发布或设备复测；真实传输和设备上的新故障处理尚未验证。
