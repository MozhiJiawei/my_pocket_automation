# DFX 结果与故障处理

每轮归档源码包、哈希清单、无授权信息的运行配置、设备日志截图和 `result.json`。账号身份特征及授权继续保留在仓库外。

每轮 Lua 使用独立构建目录，发布归档中的 `script-source.lua`，避免共享 `dist/` 被并发构建覆盖。`start-emulator.py` 在环境动作前先写 `requested-scope.json`；父轮 `emulator-start.json` 通过 `lua_run_id`、`lua_archive` 关联 Lua 轮次，子轮 `result.json` 通过 `environment_run_id`、`environment_archive` 反向关联环境轮次。范围与哈希仅供 AGENT 核对本次实际请求和版本；等待期间输入变化会拒绝本次发布，不触发自动恢复或计数。

`collect-debug.ps1` 先将设备文件拉到临时路径，核对拉取前后的设备 SHA256 与本地 SHA256，再替换正式归档。整轮归档完成后，有对应轮次的结束标记，或现有授权接口确认触动精灵空闲，才复核哈希并逐个删除设备副本，主日志最后删除。无结束标记时每次删除前重新检查空闲状态；运行中、状态未知或文件变化时保留设备副本。失败现场随归档保留，运行资源不参与清理；授权只通过进程环境临时传递。

## 性能与日志

设备日志分为 INFO、错误、Profile三类，文件分别为 `daily_<轮次>.log`、`daily_<轮次>_error.log`、`daily_<轮次>_profile.log`；按需创建。INFO 保留角色与任务起止、最终验收、恢复重试和结果；页面、等待、识别、列表扫描及输入细节属于 DEBUG，仅 `--verbose-logs` 开启。事件名和结果格式保持电脑验收兼容。

默认不归档常规过程、完成卡片及葫芦空列表截图；完成依据保留在 Lua 核验日志与完成账本。师门、抓鬼寻物通过 `dfx.materials.prepare()` 核验首屏，再由识别器逐页调用 `capture_find()`，在同一轮滚动中截图、识别和复核作答，不预采整题再回滚重扫。未命中时采至末页；题目未知时复用 `catalog.capture()` 只读采集。拼图保存操作前原图。游戏交付核验成功后清理临时文件，失败、单步退出待验收或异常时保留；切换角色或重试不能混用素材。提前成功或页面退出留下的缺页素材标记不完整，不拼接为完整回归题。

寻物的页面状态、题干和行边框在同一帧读取，仍须连续三次观察到行边框稳定才保存本页；淡出的滚动条不参与稳帧判断。题干只用于流程连续性核验，每个采样点的 RGB 通道相对本题首屏最多允许1级色差，参考不随翻页漂移；候选识别特征、匹配阈值和点击复核保持独立。真实换题、页面退出或持续移动时停止并保留已有素材。

运行器采集后用 `failure_materials.assemble()` 复用 `compose_rows()` 生成含题干的去重长图；`result.json.recognition_materials` 记录每题原图路径与待检查结果。缺页、起点未知、拼图裁切、去重物品区不足2760像素均不得作为完整用例；达标也只标记待视觉核验，仍须检查首尾和接缝后入队。失败现场、领奖收据及显式采集继续保留；任务返回的失败截图可由主循环复用。`--routine-screenshots` 仅控制过程截图，不关闭识别素材采集。

Profile记录运行总时长，以及识别、页面判断、寻物、输入、身份核对和任务的调用次数、耗时和抛出异常数。底层识别与页面判断是高频调用，只用 `os.clock` 累计 CPU 时间与最大 CPU 时间，不在循环中读取文件；寻物、输入、身份核对和任务的实际耗时在阶段边界从 Android `/proc/uptime` 读取（通常10毫秒精度），不可用时降级为秒级时间。CPU 时间不能当作包含等待的实际耗时。各作用域包含内部调用与等待，不能将嵌套作用域的累计耗时相加当作总耗时；业务暂停不等同函数抛出异常，应结合错误日志判断。结束时输出聚合值，不逐调用写文件。

寻物过程另用 `dfx.find_profile` 在当前题目的素材对象中暂存统计，最多首屏准备和7页记录、每页最多10个实际点击坐标。只在准备、稳帧、截图、匹配、滚动、点击和结果等待等阶段边界采样，候选循环只递增工作量计数，不逐候选计时、不额外截图。成功交付随素材一起丢弃；正常单步成功但待交付也不输出过程 Profile。失败保留素材时才输出一次 `scope=find_failure` 摘要及最多8行 `scope=find_page`，写入原有 `_profile.log`，不逐步骤刷日志。阶段字段按 `开始偏移毫秒,实际耗时毫秒,CPU毫秒,调用次数` 排列；偏移从本题首屏准备前算起，`other_ms` 是未被这些阶段覆盖的时间。页记录包含题目、特征数、候选与搜索次数、匹配及脚本已发送的选择数、实际点击坐标和已观察到的页面状态；它们是调试证据，不是游戏验收或标注真值。未扫描到的页不补造记录。

采集器在 `result.json.recognition_materials[].failure_profile` 关联该题摘要、逐页阶段数据、对应原图及 Profile 日志路径。前缀、角色和任务必须相符；缺页及首屏快照前失败也可保留诊断，但不改变素材完整性结论。没有 Profile 的历史归档保持兼容。对照每页原图中的倒计时与开始偏移、各阶段耗时，可区分未扫完、匹配未命中、点击或页面变化；未被明确识别的页面变化仍保留原始原因，不自动断言为超时。

师门与葫芦收尾同样提供任务、页面及师门小游戏 Profile。启用 Profile 时，日志前缀包含本轮单调时钟 `elapsed_ms`；可按相邻状态变化计算互不重叠的时间区间，再与任务总耗时、识别统计交叉核对。脚本启动前的授权、构建、发布及电脑端开发回归时间另计，不能归入游戏执行时间。

任一角色身份、所选任务或返回首页核验失败，主循环立即停止，不跳到后续任务或角色；未完成状态不能报告成功。寻物识别失败先保存现场，只有已出现游戏的免费重试页面才重试，最多3次；入口、身份、通信等错误不适用。该 Lua 内部重试计数与待重试标记只保留在本次 Lua 运行的内存中，与外部恢复分别计数。启动恢复从游戏页面重建未完成任务，同日同身份已核验的完成布尔状态可复用；调试归档不作为业务进度。

两个原子命令完成本次运行后返回原始结果与证据，后续判断由 AGENT 按 [运行期失败工作流](</D:/Agent Repo/my_pocket_automation/AGENTS.md>) 执行；命令和手工记录模板见 [设备运行期恢复](</D:/Agent Repo/my_pocket_automation/scripts/device/README.md>)。AGENT 须读取 `result.json`、日志、失败画面和源码版本，确认首个故障及实际运行状态。仅拼图类失败沿用 [标注、还原、自查、固化、校准、回归与 Lua 受控复测](</D:/Agent Repo/my_pocket_automation/scripts/perception/README.md>)；其他运行期失败保持已验证版本和原范围。

每轮 `debug-runs/<轮次>/` 独立归档；AGENT 在 `debug-runs/recovery/vm-<实例索引>/恢复记录.md` 关联目标、原范围、版本哈希、故障证据、动作前预记次数、结果和下一步。原自动恢复历史继续保留，未解除故障须由 AGENT 承接。故障是否解除由 AGENT 根据新证据判断，不能根据原因文字变化、重启或新会话清零。所有恢复记录都是诊断证据，不写入业务完成账本，也不供 Lua 重建业务进度。

## 如何判断结果

| 字段 | 含义 |
| --- | --- |
| `host_status` | 电脑端完成、启动未知、超时、通信失败或业务证据不足 |
| `launch_status` | 未尝试、已接受、响应未知；响应未知不代表没有启动 |
| `script_status` | 设备日志证实正常退出、失败，或证据不足 |
| `business_status` | 已观察、运行中、完成、未全部实现、暂停、阻塞或失败 |
| `termination_reason` | 设备业务终止原因；同时保留原始 `device_summary` |
| `last_device_status` / `may_still_be_running` | 最后观察到的设备状态，以及是否可能仍在运行 |
| `collection_status` | 采集是否尝试、完成或失败；完成不保证业务证据充分 |
| `expectation_met` | 已取得的证据是否符合本次调测步骤，不等同整日成功 |
| `requested_scope` | 本次请求的角色、任务、步骤及等待范围；目标另由 `vm_index`、`mumu_dir` 记录 |
| `source_sha256` / `device_tools_sha256` | Lua 源码及设备工具的逐文件哈希 |
| `accounts_sha256` / `account_resources_sha256` | 角色配置及逐角色身份、选择资源哈希 |
| `run_config_sha256` | 本轮生成的无授权运行配置哈希 |
| `environment_run_id` / `environment_archive` | 调用本轮 Lua 的环境轮次及归档位置；直接运行 Lua 时无父环境轮次 |

原始日志的 `task_result` 保留任务 `status`、`reason` 及当时角色上下文，`home_verified` 保留角色与任务后的回主页验收。名单、身份、任务及页面核验日志与画面供 AGENT 交叉判断故障及是否解除；它们不生成自动故障分类、验收边界、恢复事件列表或控制令牌。任务完成与回主页分别核对，原始原因不得因外部恢复推断而改写。证据不足时如实保留未知并取证，不能从最后一次启动输出推定业务完成。

`daily_complete` 只有全部配置角色的师门、抓鬼、副本与葫芦收尾都完成时才为真；指定角色、任务子集或师门后葫芦调测均不能报告完整日常。主循环或完整步骤遇到暂停，电脑端返回失败；单步调测只有符合该步骤明确预期原因的暂停才接受，未知画面暂停不能冒充预期结果。

每次单次运行调用启动入口前先记录“启动未知”。响应丢失、等待超时或通信失败后，尽力查询设备状态并采集本轮证据，持久化异常结果并返回 AGENT。Lua 仍在运行或状态未知时不从外部强停、不重发启动、不覆盖代码；录制、他人忙碌或无法确认空闲时不接管，也不因游戏进程是否存活而发起操作。异常信息只记录类型，避免归档授权信息。采集或清理的次生异常不能覆盖首个异常或丢失已有证据。

`ts-cli.ps1 deploy/run` 共用已认证的空闲检查，只有状态 `f00` 才发布。直接 `deploy` 因此也需要 `TOUCHSPRITE_AUTH`；通过 `run-daily.py` 使用现有外部授权即可。设备状态未知时拒绝发布。采集不需要授权。

Lua 故障处理分别尝试写首个错误、保存截图、记录退出；某一路失败不会阻止其他诊断。文件日志不可用时尝试 `nLog`，但不保证电脑端能取得该输出。配置加载等早期错误可能没有设备日志，运行器必须判为证据不足，并保存电脑端结果。

## 离线验证

```powershell
python scripts/device/build.py
python scripts/test.py --group 其他
```

- `test_dfx_runner.py`：模拟发布／设备／采集，注入响应丢失、等待超时、通信错误、采集超时、清理失败、缺失日志和业务暂停，验证每轮持久化结果、保留首个错误且不重发启动。
- `test_dfx_device_failures.py`：执行真实 Lua 入口，替换设备及任务能力，验证日志／截图失败和初始化错误的诊断兜底、返回主页失败的显式结果。
- `test_dfx_publish.py`：执行实际 PowerShell 发布决策块，替换 API 和发布动作，验证忙碌／未知状态拒绝发布、空闲部署不启动、空闲运行仅启动一次；AST 检查不存在另一处绕过检查的发布调用。

这些测试不调用 ADB、HTTP，不读取真实授权或角色资料，不启动副本；离线注入故障不能替代真实设备验证。

## 多角色证据

整轮汇总记录预期角色数、已完成角色数以及所选任务完成状态。电脑验收逐个核对配置角色×所选任务的结果，任一缺失、重复、未完成或额外角色都不能报告成功；不能只看最后一个角色或一个 `done`。

`result.json` 另存各角色副本领取政策。恢复领取只认明确收据，已发出请求但结果不明时不重复发送；跨角色进度不得共享。
